# 0003 The native shim is a Rust cdylib

Status: accepted, 2026-11-12; amended 2026-11-12 with the C++ exception boundary.

## Context

`bun:ffi` `dlopen` cannot pass or return C structs by value, cannot start threads, and cannot install signal handlers.
The imported binding compiled a C shim at start-up with `bun:ffi` `cc` (TinyCC).
The project rule is that code that is not TypeScript is written in Rust.

## Decision

The shim is the Rust crate in `native/`, built as a cdylib per platform and shipped in each platform package next to libduckdb.
It declares the DuckDB C API through `libduckdb-sys` 1.20000.1 (DuckDB 2.0.0) with default features off, so it links dynamically to the shipped libduckdb with no download and no bundled copy.
It is linked with an rpath of `$ORIGIN` on Linux and `@loader_path` on macOS, so it finds the libduckdb beside it.
The linux-x64 release build runs in the `rust:1.99.1-bookworm` image, so it needs glibc 2.36 or newer.
`native/ABI.md` is the contract between the shim and `src/bindings/`.

### Amendment: the C++ exception boundary

The fuzz tests found that many libduckdb C functions let a C++ exception escape on bad input, such as `duckdb_to_date` with month 0 behind `DuckDBDateValue.fromParts`, and `duckdb_get_blob` on a value that does not cast.
Through `bun:ffi` the exception aborts the process, while the official binding under Bun throws a catchable `Error`.
Rust cannot catch it: the `std::panic::catch_unwind` documentation for Rust 1.99.1 says that catching a foreign exception either aborts the process or returns an opaque error, and which one is unspecified, and neither gives the message.

So the boundary is the one exception to "code that is not TypeScript is Rust": C++ in `native/cpp/`, compiled into the shim by the `cc` crate with every warning an error.
`boundary.cpp` keeps a per-thread flag and message, and `capi.cpp`, generated by `bun run gen:ffi`, has one wrapper per C function JavaScript calls, typed from the function's own declaration, that catches any exception.
The by-value wrappers moved there from Rust, so every C API call from JavaScript crosses the boundary.
A cdylib exports only Rust's symbols, so Rust exports `dbs_capi_table`, which hands JavaScript the wrappers' addresses for `bun:ffi` `linkSymbols`, and the flag and message accessors.
JavaScript reads the flag after each call and throws DuckDB's message as an `Error`; `native/ABI.md`, "C++ exceptions", has the contract.

## Rejected options

- Keeping the TinyCC shim: compiles C on every start, and the rule forbids new C.
- Hand-written or bindgen declarations: `libduckdb-sys` already ships bindings generated from DuckDB 2.0.0's `duckdb.h`.
- Catching only in the functions known to throw: the C API does not document which functions throw, and a new DuckDB version can add one; a wrapper on every function costs one direct call and a flag read.
- Catching in Rust with `extern "C-unwind"` and `catch_unwind`: unspecified for a foreign exception, as above.
- Validating arguments in JavaScript before the call: it would copy DuckDB's checks for each function, and miss the ones it does not copy.
- A second shared library for the C++ wrappers: one more native file per platform package for no gain over linking them into the shim.

## Consequences

Contributors need the Rust toolchain pinned in `rust-toolchain.toml` and a C++17 compiler to build the shim.
The shim links the platform's C++ runtime, as libduckdb already does (`libstdc++` on Linux, `libc++` on macOS).
There is no runtime compile step, and `bun build --compile` embeds two native files per platform.
